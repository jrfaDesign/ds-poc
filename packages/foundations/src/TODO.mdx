# Design System White-Label — Analysis & Improvement Plan

## Architecture Viability Assessment

### Verdict: **VIABLE** — with targeted improvements

The current MVP architecture is **fundamentally sound** for white-label with API-driven theme loading. The core design decisions — Zod validation, runtime CSS variables, deep merge capability, and the contract system — provide a strong foundation. However, several gaps must be addressed before production deployment.

### What Works Well

| Strength                                    | Why It Matters for White-Label                                                                                                         |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Zod validation** (`TokensSchema.parse()`) | API themes are fully validated at runtime; malformed data fails fast                                                                   |
| **Deep merge** (`mergeTheme()`)             | Partial API themes merge with defaults; only brand-specific overrides needed                                                           |
| **Runtime CSS variables** (`applyTheme()`)  | Themes are hot-swappable; no rebuild required                                                                                          |
| **Contract system**                         | Semantic tokens (actions, surfaces, feedback) can be overridden per brand                                                              |
| **Class-based dark mode**                   | Mode switching is independent of theme; no JS re-run needed                                                                            |
| **Type safety**                             | TypeScript types enforce token structure across all packages                                                                           |
| **Generic contract resolution**             | Both Tailwind and RN adapters resolve any flat contract property automatically. Adding/removing tokens requires zero adapter edits.    |
| **Auto-derived types**                      | `ResolvedComponents` type is derived from the Zod schema. Radii → `number`, colors → `string`. Full type safety with zero maintenance. |

### ~~Critical Issues Found~~ — Resolved Items

## Improvement Plan

### HIGH PRIORITY — Must Fix for White-Label

#### ✅ 1. Fix `codegen.js` sync with `index.ts` — DONE

**Problem:** `codegen.js` is manually maintained and has drifted from the canonical TypeScript arrays.

**Solution implemented:**

- `packages/foundations/scripts/generate-codegen.mjs` — parses `index.ts` via the TypeScript Compiler API, extracts all exported const arrays and objects, writes `codegen.js`
- `packages/foundations/scripts/verify-codegen.mjs` — CI check that fails if `codegen.js` is out of sync
- `packages/foundations/package.json` — `generate:codegen`, `generate:tokens`, `verify:codegen` scripts
- `FLAT_CONTRACT_PROPERTIES.components` — **auto-derived** from `ComponentsPresetSchema` property names by the generate script, eliminating the need to maintain a separate manual array

---

#### 2. Add dynamic theme loading infrastructure

**Problem:** `useTheme` hook hardcodes theme imports. For white-label, themes must be fetched from an API.

**Current state** (`apps/tailwind-sample/src/hooks/useTheme.ts:1-22`):

```typescript
import { defaultTheme, cagTheme, ... } from '@repo/themes';
const themes: Record<ThemeKey, Tokens> = { default: defaultTheme, ... };
```

**Required changes:**

1. **Create a `ThemeProvider`** in `@repo/ui-web-tailwind` that:
   - Accepts a `themeResolver` function or `themeUrl` prop
   - Fetches theme from API on mount / when brand changes
   - Validates response with `TokensSchema.parse()`
   - Provides loading/error states
   - Falls back to default theme on error

2. **Create a `useRemoteTheme` hook** that:
   - Manages fetch lifecycle (loading, error, success)
   - Caches fetched themes in memory (and optionally `localStorage`)
   - Re-fetches when brand ID changes
   - Provides `refetch` for manual refresh

3. **Update `applyTheme`** to be idempotent and safe for re-invocation (already is — verified)

**Proposed API:**

```tsx
<ThemeProvider brandId="cag" fallback={defaultTheme} onError={(err) => console.error(err)}>
	<App />
</ThemeProvider>;

// Or with hook:
const { theme, loading, error } = useRemoteTheme('cag');
```

**Files to create/modify:**

- `packages/ui-web-tailwind/src/components/ThemeProvider/ThemeProvider.tsx` (new)
- `packages/ui-web-tailwind/src/components/ThemeProvider/useRemoteTheme.ts` (new)
- `packages/ui-web-tailwind/src/index.ts` (export new components)
- `apps/tailwind-sample/src/hooks/useTheme.ts` (migrate to use new infrastructure)

---

#### 3. Prevent FOUC (Flash of Unstyled Content)

**Problem:** Theme loads asynchronously after API fetch. Initial render shows unstyled content.

**Solutions:**

1. **SSR-compatible initial theme:** Provide a default theme synchronously before API fetch completes
2. **Loading state:** Show a minimal loading skeleton or spinner while theme loads
3. **Synchronous theme application:** Use `useLayoutEffect` (already done in `useTheme`) to apply theme before paint
4. **Theme preloading:** Load theme CSS variables in a `<script>` tag before React mounts

**Implementation:**

```tsx
// In ThemeProvider
const [theme, setTheme] = useState<Tokens>(fallback); // Synchronous default

useLayoutEffect(() => {
	fetchTheme(brandId).then((remote) => {
		setTheme(remote);
		applyTheme(remote);
	});
}, [brandId]);
```

**Files to modify:**

- `packages/ui-web-tailwind/src/components/ThemeProvider/ThemeProvider.tsx`
- `apps/tailwind-sample/src/main.tsx`

---

#### ✅ 4. Complete `CONTRACT_PREFIX` mapping — DONE

**Problem:** `applyTheme.ts` had a local `CONTRACT_PREFIX` missing entries for `feedback`, `toggle`, and `components`.

**Solution implemented:** `applyTheme.ts` now imports `CONTRACT_PREFIX` and `CONTRACT_STRUCTURE` from `@repo/foundations`. Local definition removed. The canonical `CONTRACT_PREFIX` in `index.ts` includes all 7 entries.

---

#### ✅ 4b. Generic contract resolution (React Native) — DONE

**Problem:** The RN adapter had 10 lines of manual per-property resolution code for `components`. Adding a new property required editing the adapter.

**Solution implemented:**

- `applyTheme.ts` component resolution changed from manual per-property code to a generic loop
- `components` removed from `knownContracts`, flows through the generic `extraContracts` resolver
- `ShadowColorSchema` handling added to the generic loop (handles `{light, dark}` pairs)
- Adding/removing properties from `ComponentsPresetSchema` requires zero adapter edits

---

#### ✅ 4c. Auto-derived `ResolvedComponents` type — DONE

**Problem:** The RN adapter used `Record<string, string | number>` for `components`, providing no type safety.

**Solution implemented:**

```typescript
// packages/foundations/src/index.ts
type ComponentsRaw = z.infer<typeof ComponentsPresetSchema>;
export type ResolvedComponents = {
	[K in keyof ComponentsRaw]: ComponentsRaw[K] extends { type: 'radii' } ? number : string;
};
```

- `RadiiRef` properties → `number` (px value)
- Color properties (`ShadowColorSchema`, `ColorTokenRefSchema`) → `string` (hex value)
- Imported and used in `applyTheme.ts`, replacing the generic `Record<string, string | number>`
- Full type safety: typos and unknown properties produce compile errors

---

#### ✅ 4d. Auto-generated component `@utility` classes — DONE

**Problem:** Component CSS utility classes (`bg-components-*`, `rounded-*`) were hardcoded in `generate-theme-css.mjs`. Adding a new property required a manual CSS edit.

**Solution implemented:** `generate-theme-css.mjs` now auto-generates component utility classes by iterating `FLAT_CONTRACT_PROPERTIES.components`:

- Color properties: strip `Bg` from name → `bg-components-{name}` utility
- Radii properties: strip `-border-radii` or `-radii` → `rounded-{name}` utility
- `FLAT_CONTRACT_PROPERTIES.components` is auto-derived from `ComponentsPresetSchema` by `generate-codegen.mjs`

### MEDIUM PRIORITY — Should Fix

#### 5. Optimize `applyTheme` performance

**Problem:** `applyTheme` creates hundreds of CSS variables via individual `setProperty` calls on every theme switch. Visible delay on lower-end devices.

**Solutions:**

1. **Batch DOM writes:** Collect all property changes, then apply in a single `requestAnimationFrame`
2. **Diff detection:** Only update variables that actually changed between old and new theme
3. **CSS `@property` transitions:** Enable smooth color transitions when theme changes

**Files to modify:**

- `packages/ui-web-tailwind/src/adapters/tailwind/applyTheme.ts`

---

#### 6. Add error boundary for theme validation

**Problem:** If API returns a malformed theme, `TokensSchema.parse()` throws and crashes the app without fallback.

**Solution:** Wrap `TokensSchema.parse()` in try-catch, log validation errors, fall back to default theme.

**Implementation:**

```typescript
function safeParseTheme(data: unknown, fallback: Tokens): Tokens {
	try {
		return TokensSchema.parse(data);
	} catch (err) {
		console.error('[Theme] Validation failed:', err);
		return fallback;
	}
}
```

**Files to modify:**

- `packages/ui-web-tailwind/src/components/ThemeProvider/useRemoteTheme.ts`
- `packages/themes/src/mergeTheme.ts` (optional: add safe variant)

---

#### 7. Add theme versioning and migration

**Problem:** If token schema changes between versions, API themes might break silently.

**Solution:** Add `version` field to `TokensSchema`, implement version-aware migration functions.

**Files to modify:**

- `packages/foundations/src/index.ts`
- `packages/ui-web-tailwind/src/components/ThemeProvider/useRemoteTheme.ts`

---

#### 8. Deduplicate `hexToRgba` logic

**Problem:** `resolveAlpha` in `index.ts` and `hexToRgba` in `applyTheme.ts` are nearly identical.

**Status:** Still open. This is the only remaining Phase 1 item. Low priority — the duplication is contained (one function in each file) and doesn't affect correctness.

**Solution:** Export `hexToRgba` from `@repo/foundations` and import in `applyTheme.ts`.

**Files to modify:**

- `packages/foundations/src/index.ts` (export `hexToRgba`)
- `packages/ui-web-tailwind/src/adapters/tailwind/applyTheme.ts` (import and use)

---

### LOW PRIORITY — Nice to Have

#### 9. Add SSR support

**Problem:** `applyTheme` uses `document.documentElement` directly, which fails in SSR/Next.js.

**Solution:** Add `typeof document !== 'undefined'` guard. Return CSS variable string for SSR rendering.

**Files to modify:**

- `packages/ui-web-tailwind/src/adapters/tailwind/applyTheme.ts`

---

#### 10. Simplify CSS variable bridge layer

**Problem:** The `@layer base` bridge variables (`--color-*: var(--*)`) in `tailwind-theme.css` add complexity.

**Solution:** Update component helpers to reference `--ct-*` or `--action-*` directly, eliminating the bridge layer. Reduces CSS file size and simplifies the variable chain.

**Files to modify:**

- `packages/ui-web-tailwind/src/adapters/tailwind/tailwind-theme.css`
- `packages/ui-web-tailwind/scripts/generate-theme-css.mjs`
- `packages/ui-web-tailwind/src/components/shared/cssVars.ts`

---

#### 11. Theme persistence for API themes

**Problem:** `localStorage` only stores theme key, not the full theme data. If API is slow, app re-fetches on every load.

**Solution:** Cache fetched themes in `localStorage` with TTL (e.g., 24 hours).

**Files to modify:**

- `packages/ui-web-tailwind/src/components/ThemeProvider/useRemoteTheme.ts`

---

#### ✅ 12. Typography contract letter spacing handling — DONE

**Problem:** `letterSpacing` is optional in `TypographyContractValueSchema`, but `@theme inline` always emitted the variable, producing empty CSS values.

**Solution implemented:**

- `applyTheme.ts` conditionally emits `letterSpacing` only when the contract defines it
- `generate-theme-css.mjs` uses `var(--*, normal)` fallback in the `@utility type-*` blocks
