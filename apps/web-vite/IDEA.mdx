# Cross-Platform Design System: Research & Decision Framework

## 1. Executive Summary

Building a cross-platform design system (web + React Native) is an investment in consistency, developer velocity, and brand fidelity. The core challenge is not about choosing a styling library - it is about **designing the right token architecture** and **building platform-specific rendering adapters** on top of it.

The industry is converging on a layered model:

```
Design Tokens (platform-agnostic) → Adapters (per-platform rendering) → Components
```

This report surveys the landscape, compares token approaches, evaluates technology options, and provides a decision framework - without prescribing a single path.

Throughout this report, we distinguish two perspectives:

- **Design System Builders**: the core team defining tokens, roles, themes, adapters, and components. They need a flexible schema, extensible architecture, build tooling, and CI/CD.
- **Design System Consumers**: product teams that USE the design system in their applications. They need stable APIs, clear documentation, predictable theming, and an easy migration path.

Both perspectives are essential. The token architecture, technology choices, and release model must serve both.

## 2. Token Architecture: Two Approaches

The most critical decision is how we model color tokens. Two approaches dominate:

### 2.1. The Simpler Auto-Resolve Approach

Some design systems define a compact set of color tokens and let components auto-resolve paired values.

**Example token set:**

- Base colors (`blue`, `red`, `green`, ...)
- Neutral colors (`gray50`, `gray100`, ... `gray900`)
- Semantic colors (`success`, `error`, `warning`, `info`)
- Background options (`bg_white`, `bg_light`, `bg_light_variant`, `bg_dark`, `bg_dark_variant`)
- Foreground tokens (3 levels for light mode, 3 levels for dark mode)

**How it works:** When a consumer passes `bg_dark` to a component, the component auto-resolves both the background AND the on-background foreground color. The developer doesn't explicitly choose the text color - the system infers it.

One example of this approach organizes colors into a `ColorPalette` with mandatory colors (primary, neutral, semantic), supporting colors (secondary, tertiary), and role-based tokens (`bg_*`, `fg_*`, `cta_*`). Each role carries an auto-resolve metadata structure:

```typescript
type ColorPaletteRoleTokenInfo = {
	token: ColorPaletteOptions; // the color to use
	onTokenFgBase: ColorPaletteRoleForegroundBaseOptions; // which fg to pair
	onToken: ColorPaletteOptions | undefined; // override if needed
};
```

When a component receives `bg="bg_dark"`, it looks up `onTokenFgBase` to resolve the foreground to `fg_dark_1`. Backgrounds come in core variants (`bg_white`, `bg_dark`, `bg_dark_variant`, `bg_light`, `bg_light_variant`) and semantic variants (`bg_dark_semantic_error`, etc.). Foregrounds have three contrast levels (`fg_light_1/2/3`, `fg_dark_1/2/3`). Component-specific overrides live in `theme.components`.

This approach is compact and fast to implement, but as discussed in the cons below, it struggles when design needs variations the auto-resolution doesn't cover.

**Pros:**

- Fast to implement and understand
- Fewer decisions per component - convenient defaults
- Less token surface area to maintain
- Works well for small teams or single-brand products

**Cons:**

- Design often needs slight variations the auto-resolution can't accommodate
- Adding a new surface variant (e.g., a subtly different card background) requires either (a) extending the auto-resolution logic, or (b) overriding it - both add complexity
- Dark mode can be unpredictable: auto-resolution may not produce the intended contrast or aesthetic
- Limited "contracts" between design and engineering - designers can't express precise surface/text/border intent without workarounds

### 2.2. The Role-Heavy Approach

This model defines explicit semantic roles for every use case, each with its own `{light, dark}` value pair. No auto-resolution - full control.

**Example roles (60+):**

```
// SURFACES
surface          → base background
surfaceAlt       → cards, panels, sheets
surfaceRaised    → modals, popovers
surfaceSunken    → input fields
surfaceInverse   → inverted contexts

// TEXT
text             → body, headings
textSecondary    → labels, metadata
textTertiary     → captions, timestamps
textInverse      → on inverted surfaces
textBrand        → brand-colored text

// BORDERS & STRUCTURE
border           → standard borders
borderStrong     → high-contrast outlines
borderWeak       → subtle borders
divider          → separators
focusRing        → accessibility focus

// ACTIONS - Primary
actionPrimaryBg / Hover / Active
actionPrimaryFg
actionPrimaryBorder
actionPrimaryDisabledBg / Fg / Border

// ACTIONS - Secondary, Ghost, Link (same pattern)

// FEEDBACK - Error, Success, Warning, Info
errorBg / Fg / Border / BgInverse / FgInverse
successBg / Fg / Border / BgInverse / FgInverse
// ... same for warning, info
```

**How it works:** A button component explicitly references `actionPrimaryBg` for its background, `actionPrimaryFg` for its text, and `actionPrimaryBorder` for its border. No inference. Each role has a defined `{light, dark}` color mapping, so dark mode is deterministic.

**Pros:**

- Maximum control - designers can specify every visual aspect
- Clear contracts between design and engineering: "use `surfaceAlt` for cards" is unambiguous
- Predictable dark mode - every role has explicit light and dark values
- Scales to many brands/products - each brand can override specific roles
- Better for accessibility - explicit roles make contrast auditing straightforward

**Cons:**

- More upfront effort to define and maintain 60+ roles
- Can feel verbose for simple components (a basic alert needs `errorBg`, `errorFg`, `errorBorder`)
- Requires discipline - teams must use roles rather than raw colors
- Steeper learning curve for new developers

### 2.3. Trade-off Analysis

| Dimension               | Simpler Auto-Resolve | Role-Heavy     |
| ----------------------- | -------------------- | -------------- |
| Time to implement       | 1-2 weeks            | 3-6 weeks      |
| Design ↔ Eng contracts  | Few, implicit        | Many, explicit |
| Dark mode reliability   | Variable             | Deterministic  |
| Multi-brand flexibility | Limited              | High           |
| Learning curve          | Low                  | Medium         |
| Component verbosity     | Low                  | Medium-High    |
| Scales to 10+ products  | ❌ Struggles         | ✅ Handles     |
| Designer autonomy       | Limited              | Full           |

**The Product Developer Perspective**

Product teams that USE the design system (not build it) face a different set of needs:

- **Predictable APIs** - a Button or Card should work the same way in every product
- **Sensible defaults** - most cases should "just work" without deep token knowledge
- **Progressive disclosure** - simple use cases are simple; advanced customization is available but opt-in
- **Consistent behavior** - dark mode, hover states, and focus rings are handled automatically without manual wiring
- **Clear error messages** - if something is misconfigured, the error should say exactly what and where
- **Fast iteration** - hot reload works, no build surprises, no cryptic runtime failures

A simpler auto-resolve system scores higher on "just works" but lower on "advanced customization." A role-heavy system scores higher on "I can make it look exactly like the design" but lower on "I don't need to understand 60+ tokens to build a form." Both approaches need good documentation, Storybook examples, and prop-type autocomplete to serve product teams well.

### 2.4. Why the Role-Heavy Approach Wins for Multi-Brand / White-Label

For a multi-brand / white-label scenario with potentially hundreds of brands, the role-heavy approach is the right choice. Auto-resolve systems break down because they assume a finite set of contrast relationships within a single brand identity. When every brand has its own color relationships, auto-resolution becomes a guessing game - the system cannot infer the "right" foreground for a background it has never seen.

**The role-heavy approach solves this:** each brand provides explicit `{light, dark}` values for every role. No inference. Dark mode is deterministic per brand. Components behave predictably because they reference semantic roles, not guessed contrasts.

A well-designed role system (like the one defined by a Zod-schema approach) makes extension controlled and safe:

- Adding a new role is a single entry in the schema + a `{light, dark}` mapping in each theme
- Zod's `.strict()` rejects unknown keys - brands cannot inject ad-hoc tokens
- `z.infer<typeof TokensSchema>` keeps types in perfect sync across the entire codebase
- Component tokens reference existing roles via `RoleRefSchema`, so consumers never touch raw colors

**What this means for molecules (Button, Input, Card, etc.):**

Each component should be built using semantic roles, not raw colors. A Button uses `actionPrimaryBg`, `actionPrimaryFg`, `actionPrimaryBorder` for its primary variant. When a consumer passes `variant="primary"`, the component resolves to those roles - which change per brand and per mode automatically.

| Aspect           | How the role system helps                                                                                  |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| **Variants**     | Each variant maps to a fixed set of roles. Adding a new variant is a new mapping, not a new color decision |
| **Props**        | Controlled by the component schema - consumers can only choose from validated options                      |
| **Multi-brand**  | Each brand overrides the role values independently; the component code does not change                     |
| **Dark mode**    | Every role has an explicit dark value per brand - deterministic, no guessing                               |
| **Future roles** | New roles slot into the existing schema without breaking existing components                               |

**Design consideration:** Each role requires deliberate design intent - a role should only exist if it serves a real use case. The schema makes it easy to add roles, but the discipline is in defining them thoughtfully. An exhaustive role set (surfaces, text, borders, actions, feedback) gives design the vocabulary to express every visual situation without forcing engineers into auto-resolution guesses.

**How this applies to cross-platform:** The contract (tokens, roles, component API) is shared. The component implementation (StyleX vs StyleSheet) is platform-specific. The design system controls the _what_ (roles, variants, behavior) while each platform's adapter controls the _how_ (rendering, animations, gestures).

## 3. How Other Design Systems Handle Cross-Platform

### 3.1. Web-Only Systems

**Radix UI, Shadcn/ui, MUI** - built exclusively for React DOM. They depend on browser APIs (DOM, portal, focus management) and offer no React Native support. If cross-platform is a goal, these are reference points for component API design but not adoptable directly.

### 3.2. Dual-Track Systems (Shared Tokens, Separate Components)

**Microsoft Fluent UI:** Separate `@fluentui/react` (web) and `@fluentui/react-native` packages. They share `@fluentui/tokens` but render differently per platform. Web uses Griffel (build-time CSS-in-JS), RN uses React Native primitives. Components are implemented twice, which is expensive but gives platform-native behavior.

**Adobe Spectrum:** `react-aria-components` provides headless behavior hooks that work on both web and RN. The styled `@adobe/react-spectrum` is web-only. Strategy: separate behavior (cross-platform) from styling (platform-specific).

### 3.3. Unified Systems

**Tamagui:** A single code path that compiles to web (atomic CSS) and RN (StyleSheet). Provides a full UI kit and an optimizing compiler that flattens styled components and extracts static CSS.

**Key insight:** No major design system (Fluent, Spectrum, Polaris, Carbon) has achieved true write-once cross-platform at scale. They maintain separate implementations per platform rather than unified component libraries.

## 4. Technology Deep-Dive

### 4.1. Build-Time vs Runtime

| Dimension      | Build-Time (StyleX, Panda, vanilla-extract)  | Runtime (styled-components, Emotion) |
| -------------- | -------------------------------------------- | ------------------------------------ |
| Bundle size    | ~2KB runtime (StyleX), CSS in separate files | 12-45KB JS overhead                  |
| Initial render | Zero style computation                       | 12-35ms per styled component         |
| SSR / RSC      | Native support                               | Requires workarounds                 |
| Dynamic styles | CSS variable indirection                     | Full JS expressiveness               |
| CSS file size  | Plateaus (atomic dedup)                      | Grows linearly                       |
| Debugging      | Atomic class names harder                    | Readable class names                 |

**Build-time is the industry direction.** Meta (StyleX), Vercel (Tailwind), and the Chakra team (Panda) all converge on build-time extraction. Runtime CSS-in-JS is in decline for new design systems.

### 4.2. Cross-Platform Technologies

| Technology            | Web            | React Native            | Bundled Component Library | Build/Runtime |
| --------------------- | -------------- | ----------------------- | ------------------------- | ------------- |
| **StyleX**            | ✅ Native      | ⚠️ via react-strict-dom | ❌ No                     | Build-time    |
| **react-strict-dom**  | ✅ (StyleX)    | ✅ (StyleSheet)         | ❌ Primitives only        | Build-time    |
| **Panda CSS**         | ✅ Native      | ❌                      | ❌ No                     | Build-time    |
| **NativeWind**        | ✅ (Tailwind)  | ✅ (StyleSheet)         | ❌ No                     | Build-time    |
| **Unistyles**         | ✅ Web adapter | ✅ Native (C++ JSI)     | ❌ No                     | Hybrid        |
| **styled-components** | ✅             | ✅                      | ❌ No                     | Runtime       |

### 4.3. The Token Pipeline: From Foundation to Product

A design system's architecture follows a layered pyramid - wide at the base (foundation) and narrowing toward the products. The key insight: the same token foundation feeds both the design and engineering tracks.

```
                          ┌────────────────────────────┐
                         /      Product Applications    \
                        /   (web apps, mobile apps)      \
                       ├──────────────────────────────────┤
                      /                                   \
                     /     Design            Engineering   \
                    /   (Figma, brand       (Web UI + RN UI) \
                   /    guidelines,         StyleX + SS API)  \
                  /     specs)                                  \
                 ├──────────────────────────────────────────────┤
                /     Semantic Roles / Contracts                  \
               /   (surface, text, border, action, feedback)       \
              /  shared vocabulary between design and engineering    \
             ├────────────────────────────────────────────────────────┤
            /              Design Tokens / Foundations                  \
           /   (colors · spacing · radii · shadows · gradients · fonts)  \
          └────────────────────────────────────────────────────────────────┘
```

**How it flows:**

1. **Bottom layer - Design Tokens:** Raw values defined in a schema (Zod + TypeScript). Platform-agnostic numbers, colors, and dimensions. This is the single source of truth.

2. **Middle layer - Semantic Roles:** Tokens are mapped to meaningful contracts. `surfaceAlt` means "card background" regardless of whether it renders as CSS or StyleSheet. Designers and engineers share this vocabulary.

3. **Top layer - Split into two tracks:**
   - **Design track:** Designers use the roles in Figma to define component specs, brand guidelines, and theme variations.
   - **Engineering track:** The same roles feed web components (via StyleX) and React Native components (via StyleSheet API).

**Key principle:** Token definitions should have zero dependency on rendering technology. A `spacing.md: 8` is just a number. It becomes `8px` in CSS, a raw number in RN StyleSheet, and a guideline in Figma. The pipeline handles conversion.

### 4.4. Web UI Package + React Native StyleSheet API

A practical split:

- **`@org/core`**: Typescript interfaces for tokens, roles, and component contracts. Shared between web and RN.
- **`@org/themes`**: Zod-validated theme instances (platform-agnostic)
- **`@org/web`**: Web components using StyleX, Tailwind, or Panda. Import tokens, generate CSS variables, use `.styles.ts` pattern
- **`@org/native`**: RN components using `StyleSheet.create()`. Import the same tokens, output RN style objects
- **Shared component contracts**: TypeScript interfaces for props, variants, and event handlers

Both packages consume the same validated tokens. The web package uses `stylex.create()`; the RN package uses `StyleSheet.create()`. The visual result is consistent because the source of truth (tokens) is identical.

## 5. Implementation Approaches

### 5.1. Greenfield Build

**Steps (sequential):**

1. Define the token schema (Zod + TypeScript): 1-2 weeks
2. Create default theme + theme merge utility: 1 week
3. Build Style Dictionary (or custom) pipeline to output CSS vars + RN constants: 2 weeks
4. Implement web adapter (StyleX / Tailwind / Panda): 2-3 weeks
5. Implement RN adapter (StyleSheet): 2-3 weeks
6. Build core components (Button, Text, Input, Card, Badge, Modal): 4-8 weeks per platform
7. Write docs + Storybook stories: ongoing

**Total: 3-6 months (1 person full-time) or 1-3 months (team of 2-3)**

### 5.2. Web-First with RN Later

1. Start with tokens + web components (StyleX or Tailwind)
2. Verify with existing products
3. Build RN adapter (reads same token format, outputs StyleSheet)
4. Share component contracts; implement separately per platform

This de-risks the RN investment until the token model is proven.

## 6. Migration & Timeline

### 6.1. Building the Design System

| Phase                         | Duration  | Output                                               |
| ----------------------------- | --------- | ---------------------------------------------------- |
| Token schema + validation     | 1-2 weeks | `@org/themes` + `@org/core` package                  |
| Token transformation pipeline | 1-2 weeks | CSS vars + RN constants                              |
| Core components (15-25)       | 4-8 weeks | Button, Text, Input, Card, Badge, Alert, Modal, etc. |
| Documentation + Storybook     | 2-4 weeks | Interactive docs                                     |
| CI/CD + publishing            | 1-2 weeks | Automated build + publish + versioning               |

### 6.2. Migrating Existing Products

| Product Size | Pages  | Components to Migrate | Timeline   | Risk   |
| ------------ | ------ | --------------------- | ---------- | ------ |
| Small        | 5-10   | 20-50                 | 2-4 weeks  | Low    |
| Medium       | 10-50  | 50-200                | 1-3 months | Medium |
| Large        | 50-200 | 200-1000              | 3-6 months | High   |

### 6.3. Migration Strategy: Strangler Fig

1. **Phase 0:** Adopt `@org/core` + `@org/themes` in all products - no visual change, just token availability
2. **Phase 1:** Build new features with the new design system components
3. **Phase 2:** Migrate existing pages one by one
4. **Phase 3:** Remove legacy system

**Coexistence patterns:**

- Both systems in the same bundle, CSS-namespaced
- New components use new tokens; old components still reference their own styling
- Gradual, safe replacement with no big-bang rewrite

## 7. Enabling Other Teams: Creating & Open-Sourcing the Design System

### 7.1. Why Runtime Validation Matters

When a design system is consumed by multiple product teams, trust in the system is critical. A malformed theme or misconfigured token should fail early and clearly - not silently render broken UIs.

Pure TypeScript types are **compile-time only** - they vanish at runtime. If a malformed theme file or API response enters the system, TypeScript cannot catch it. Adding a runtime validation library (Zod) on top of TypeScript provides:

| Concern                         | TypeScript only | TypeScript + Zod |
| ------------------------------- | --------------- | ---------------- |
| Compile-time type checking      | ✅              | ✅               |
| Runtime shape validation        | ❌              | ✅               |
| Descriptive error messages      | ❌              | ✅               |
| Safe parsing (reject vs coerce) | ❌              | ✅               |
| Schema composition/reuse        | ❌              | ✅               |
| Generate types from schema      | ❌              | ✅ (`z.infer`)   |

**Practical example:** A theme file with a missing `actionPrimaryBgHover` key, or a color value like `"not-a-color"`, will be caught by Zod at load time with a clear error message. Without it, the design system renders with missing styles and no clear signal about what went wrong.

Zod also enables: `TokensSchema.parse(data)` for strict acceptance or `TokensSchema.safeParse(data)` for graceful error handling with fallback themes. This is especially important when other teams extend themes for their own brands - the schema becomes the safety contract.

### 7.2. Contribution Model

- **Monorepo** with Turborepo for orchestration
- **Changesets** for automated versioning + changelog
- **Conventional Commits** enforced by commitlint
- **PR gates:** TypeScript → ESLint → Tests → Build → Visual regression (Chromatic)

### 7.3. Accelerating Adoption

When the schema is well-defined and the tooling is automated, other teams can:

- Create new brand themes by providing token values that conform to the schema - no need to understand the rendering internals
- Use components with confidence, knowing that type-safe props and runtime validation prevent misconfiguration
- Extend the system with new roles (with design input) without worrying about breaking existing components

The token schema is the contract. The monorepo + CI pipeline is the trust mechanism. Together, they make the design system safe to adopt and hard to misuse.

## 8. Decision Framework

Leadership should answer these questions to determine the right path:

| Question                                  | If answer is...      | Then...                                            |
| ----------------------------------------- | -------------------- | -------------------------------------------------- |
| How many products use the design system?  | 1-2                  | Simpler token approach may suffice                 |
|                                           | 5+                   | Role-heavy approach to avoid fragmentation         |
| Do products share the same brand?         | Yes                  | Single theme, simpler tokens                       |
|                                           | No (multiple brands) | Role-heavy for explicit per-brand control          |
| Does design ask for dark mode variations? | Rarely               | Auto-resolve may be fine                           |
|                                           | Constantly           | Role-heavy for deterministic dark mode             |
| Is RN support needed now?                 | Yes                  | Dual-adapter approach (separate web + RN packages) |
|                                           | In 6+ months         | Start with web + tokens, add RN later              |
| Team size available                       | 1 person             | Start with tokens + web only                       |
|                                           | 3+ person team       | Can tackle cross-platform from day one             |
| Risk tolerance                            | Low                  | Web-first, RN later                                |
|                                           | High                 | Web-first with RN later or dual-adapter approach   |

## 9. Key Takeaways

1. **Tokens are the foundation** - invest in getting the token schema right. It's the most leveraged decision a team can make.

2. **Zod + TypeScript** provides runtime safety that TypeScript alone cannot - critical when tokens come from external sources (CMS, Figma, brand configs).

3. **Role-heavy token models** scale better for multi-brand, multi-product orgs with complex dark mode requirements. Simpler auto-resolve models work for smaller teams with fewer products.

4. **Build-time styling is the industry direction** - StyleX, Panda CSS, and Tailwind all compile styles to static output. Runtime CSS-in-JS is a known performance liability at scale.

5. **No perfect cross-platform solution exists** - each technology has meaningful trade-offs. StyleX + react-strict-dom can bridge web and React Native, though the project's future is uncertain.

6. **The adapter pattern** (shared tokens → platform-specific rendering) is the most flexible long-term architecture. It allows web to use whatever technology makes sense and RN to use StyleSheet API independently.

7. **Migration should be incremental** - adopt tokens first (invisible change), then components page by page. The Strangler Fig pattern avoids big-bang risk.

8. **Plan for internal open-source from day one** - monorepo, Changesets, CI/CD, and contribution guidelines are table stakes for cross-team adoption.

9. **Agnostic tokens are the cross-platform bridge** - the theme is developed once in one place and imported anywhere. Complex structures like shadows (offsetX, offsetY, blurRadius, spreadRadius, color, opacity) or gradients (type, angle, stops) are defined as platform-agnostic schema values. The same shadow token becomes a CSS `box-shadow` on web and `shadowColor` + `shadowOffset` + `shadowOpacity` + `shadowRadius` in React Native. The theme never knows about platform specifics - the adapter handles translation. This is what makes the system truly cross-platform: one theme, many renders.
